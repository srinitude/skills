# Controlled comparisons

Load this file for each design step. Read it again before the last visual review.

## Outcome

Each kept design item uses a fresh material-direction pair at its true owner. This covers states, atoms, molecules, organisms, UI composition templates, screens, flows, and transitions. One pair may cover several parts when they form one owner link. The token skill owns token coverage. Each pair cites one shown option. It also cites one experiment record frozen before viewing.

## Owned relationship rule

Before rendering, name the observed user or design problem. Name the expected large change in order, meaning, use, effort, grouping, layout, or state sense. Freeze the sample, words, state, view size, input path, and other tokens. Freeze the experiment ID, hypothesis, null, measure, falsifier, and decision rule. Change one named owner link. Several values may move only when that link forms one whole.

If two values must move as a set, name that link as the one fact. State why. Do not hide many changes under one broad name.

Reject one-pixel changes, nearby token steps, near-identical options, and other pure optimization that only might help. Use them only when the user asks for that work. A small change may proceed without that request when current proof shows a defect. It may also meet a required safety, access, reading, reach, law, or platform limit. Render A and B through the same path only when current vision can see the planned effect. Inspect the full view and readable detail. Save eye, brain, touch, bad-design, bad-output, bad-practice, input-path, counterevidence, doubt, and stale parts. Pick `A`, `B`, `REVISE`, or `BLOCKED`.

## Acceptance

Apply the full gate to A, B, and the kept result. Uniqueness, standards, and familiarity must pass at once. Keep a change only if it fits the product. It must aid use or sight. It must also keep known acts clear.

The check does not force use. Cut a needless prop, layer, role, or form. Do not add it just for the pair. After retention, use small changes only to fix current defects or meet a clear user request. One fresh pair can reject a choice. It cannot prove the whole product.

Call this a controlled visual pair or controlled A/B pair. Do not claim cause in live use. That claim needs real group choice, sample, result, and study proof.

A kept low change makes all linked pairs, views, use checks, and quality proof stale. Rebuild from that point before a high item can pass.
