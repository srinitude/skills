# Controlled comparisons

## Focus intent

Before rendering a pair, freeze one focus-intent record for the primitive or relationship. Record `user_task`, `focus_target`, `focus_location`, `focus_timing`, `focus_mechanism`, `focus_reason`, `attention_sequence`, `competing_signals`, `defocus_and_recovery`, and `failure_evidence`. `focus_target` says what should receive attention. `focus_location` says where it appears. `focus_timing` says the state or moment. `focus_mechanism` says how the token relationship changes salience. `focus_reason` ties that choice to task, meaning, or risk. `attention_sequence` names first, next, later, or simultaneous targets. Multiple targets need a stated order or a reason they are simultaneous. Prominence without this context is not intent.

Change one token factor that can test the stated mechanism. Judge both the intended target and the strongest competing signal. Reject a pair that attracts attention for the wrong reason, hides required context, prevents recovery, or changes priority outside its claimed state. Treat the result as evidence for token salience capacity, not proof that a complete product directs attention well.

Read this file in Step 08, then apply it again after the last token change and before any atom consumes the tokens.

## Experiment before canonical token

Use this exact accepted sequence: register the experiment, create candidates, run the experiment, judge current pixels, lock the accepted relationship, then author the canonical token. Candidate values may exist before the lock only as labeled experimental evidence. They must not occupy canonical token paths, aliases, variables, styles, or downstream atom contracts. A rejected or blocked experiment produces no canonical token.

Keep the token frontier open until the evidence answers the frozen question. Generate materially unlike values and relationships, batch independent renders, and reject failed branches early. Current direct vision owns the selection. The deterministic record must show `experiment.status` as `run` and `token_layer_lock.status` as `accepted_locked` before canonical token bytes are written.

An atom may start only after every token owner it consumes is locked. Reopening or changing a token lock makes its aliases, variables, styles, proof specimens, atoms, and every higher consumer stale before more canonical work proceeds.

## Scope

Inventory every concrete token leaf with `$value`. Assign each leaf to one current material-direction comparison at its true relationship owner. A single material comparison may cover several leaves when they form one indivisible system relationship. Also compare the owned semantic relationships for related-item gaps, insets, groups, sections, shells, wide apertures, and part weight.

An alias does not need a separate value pair unless the alias changes a rendered relationship. Record that decision at the concrete owner instead of manufacturing a duplicate test.

## Pair contract

For one pair:

1. Link every covered token path or relationship role to one real exploration candidate and one experiment ID. Freeze its hypothesis, null hypothesis, measure, falsifier, and decision fields before viewing A or B.
2. Pass the materiality gate before rendering. Name the observed user or design problem and how the alternative could materially change hierarchy, meaning, behavior, task effort, grouping, responsive composition, or state understanding at whole-view scale.
3. Reject a one-pixel change, adjacent scale step, near-isomorphic candidate, or other pure optimization that only might help unless the user explicitly requested that optimization. A small change is not pure optimization when current evidence shows that it repairs an observed defect or crosses a required safety, accessibility, legibility, reach, compliance, or platform threshold; record that threshold and evidence.
4. Keep the specimen, content, state, viewport, input path, and every unrelated token fixed.
5. Change one named owned relationship only. If several values must move together, test that relationship as one factor and state why it is indivisible.
6. Render A and B through the same path only after current vision can plausibly distinguish their intended effect in the complete view and readable detail.
7. Inspect both with current strong vision. Record eye, brain, touch, bad-design, bad-output, bad-practice, counterevidence, uncertainty, and retained or rejected disposition.
8. Re-run the token-local noncompensating gate. A pair cannot waive source, access, familiarity, standards, uniqueness, or use failures.

Reject a pair when its material effect is absent, it is micro tuning without the explicit-request or threshold route, its candidate or experiment link is missing, its decision fields were not frozen before viewing, the renders are not meaningfully distinct, a fixed condition changed, the vision evidence is stale, or the result was chosen only because it is unusual. After a material direction is retained, apply small deterministic adjustments only to repair current observed defects or fulfill an explicit user optimization request. Do not introduce a token or relationship merely to satisfy coverage.

## Claim boundary

Call this a controlled visual comparison or controlled A/B pair. It can support a bounded design judgment. It is not a randomized live-user A/B test and cannot establish user-level causal impact without assignment, sample, outcome, and analysis proof.

Any accepted token change marks its proof specimen and every consuming atom or higher layer stale. The design-system lifecycle owner carries that invalidation upward.
