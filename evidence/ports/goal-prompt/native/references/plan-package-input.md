# Plan-package input

`goal-prompt` owns packaging for `/goal`. This reference owns the branch for a plan generated by `plan` and links back to `SKILL.md`.

`PD-002`: Load this file when the source names an existing path under `.hermes/plans/`. It defines plan-package discovery, identity, authority, and validation. The parent owns inline and ordinary file input, the fixed review gate, output naming, and the final command.

## Recognize one plan package

Treat these forms as one package when they resolve to the same slug:

- `.hermes/plans/<slug>.md`
- `.hermes/plans/<slug>/`
- Both paths in one `/plan` result or invocation

The primary file is `.hermes/plans/<slug>.md`. The companion directory is `.hermes/plans/<slug>/` when it exists. The report root is `.hermes/reports/<slug>/` when it exists. A primary file without a companion directory is still a valid single-file plan.

Reject path traversal, a symlink, an unreadable path, a path outside the active workspace, or input that resolves to more than one slug. Don't infer a relationship between unrelated paths.

## Build the package manifest

Write `<stem>.plan-manifest.json` under `.hermes/goal-prompts/`. Use workspace-relative POSIX paths and sort every file record by path.

Record:

- `schema_version: 1`
- The plan slug and primary plan path
- The companion and report roots, or `null` when absent
- For each plan-owned input file: role, path, byte count, and SHA-256
- The completion-report path and validator path when present
- The invocation snapshot path and SHA-256

Include the primary plan and every regular file under the companion directory. Include initial report control files referenced by the plan, such as `completion-report.json`, its validator, and plan-owned fixtures. Don't include execution-produced artifacts, evidence, logs, caches, bytecode, backups, or temporary files.

Resolve relative links from plan Markdown. Every required link must resolve inside the plan or report roots and appear in the manifest. Stop on a missing required link or an escape.

## Preserve authority

The plan package is authoritative. The invocation snapshot proves what selected it, but it doesn't replace the plan.

- Reuse the plan's existing `REQ-###`, `TASK-###`, `VAL-###`, `GATE-###`, artifact, and evidence IDs. Don't wrap plan paths in new requirements.
- Reuse the plan's task graph, approval gates, local completion rules, completion-report schema, and whole-plan validator.
- Preserve `READY` or `BLOCKED` exactly. A blocked plan remains blocked until its named gate closes.
- Read the primary plan first. Load each companion file at its recorded trigger before acting on the work it governs.
- Verify all plan-input hashes before the first mutation. Plan-input drift blocks execution until reviewed.
- Treat report changes created by authorized execution as expected state changes after the initial hash check. They don't rewrite the source plan.
- Keep task-local evidence separate from whole-plan proof. Overall PASS requires the plan's own closeout contract and whole-plan validator.

## Goal-file branch

For a plan package, set the goal to execute every task and close every requirement under the package's own contracts.

The source manifest must name the primary plan, companion root, report root, invocation snapshot, and plan manifest. Set `Requirement map` to the package's existing structured IDs instead of generating wrapper IDs.

Use the plan's outcome, constraints, boundaries, approval gates, stop conditions, and open questions. Don't invent a second completion contract or describe the primary and companion paths as ambiguous when their shared slug and links establish the package.

Add these execution rules before the fixed review gate:

- Verify the plan manifest and input hashes before the first mutation.
- Execute the dependency graph in task order and honor every gate and resume point.
- Keep the machine report truthful and `BLOCKED` until the plan's own PASS contract is met.
- Use the main agent for execution. Use async work only when SOUL's `Main-progress gate` passes.
- Run task-local checks during each task and the whole-plan validator only at closeout.

## Validate

Require all checks below:

- Exactly one slug, one primary plan, and no path or symlink escape
- Deterministically sorted manifest records with fresh byte counts and SHA-256 values
- Every required companion and report-control link exists and is represented
- No execution output or sensitive content was copied into the goal package
- Existing plan IDs and status were reused without wrapper requirements
- The goal file names the package's own completion report and whole-plan validator when present
- The general `goal-prompt` validation and fixed review gate still pass
