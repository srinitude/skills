# Skill scope and independent variants

Load this owner through `mise run resolve-scope` before a skill write and through `mise run variant` before creating, adapting in place, or refreshing a variant. The [scope contract](skill-scope-contract.md), linked by the generation contract and loaded through `mise run validate`, owns the frontmatter and resolution rules. This file owns the adaptation workflow and its acceptance boundary.

## Choose intended availability

Exactly two scopes exist. `user` means intended to be available to the user across projects. `project` means intended for a specific project or repository. Generic instructions can belong to either scope. Store the designation once, in `metadata.scope` in SKILL.md. Derive the labels user-level and project-level from that value. Other metadata remains intact. This is a repository convention inside the standard metadata extension point.

Resolve scope before writing. Honor the user's explicit choice. For an update, preserve an existing valid value unless the user requests a change. For missing metadata, infer only from unambiguous intended use and authoritative context. A registry path, current directory, or generic wording is insufficient. When evidence is missing or conflicts, ask once: “Should this skill be available across your projects (user) or for one specific project (project)?” Hold the affected write until answered.

Use `mise run resolve-scope -- --skill <source>` to preserve a designation, or add `--scope user` or `--scope project` for an explicit choice. For a legacy source or new skill, `--evidence <file>` accepts an array of objects with `scope`, `source`, and `intended_use`. The model must verify that each cited source is authoritative and actually states that availability. The resolver checks agreement and record shape; it cannot infer authorial intent from arbitrary strings. It never writes.

Prepare creation with `mise run new -- --name <name> --description "Use when ..." --scope user --dest <authoring-parent> --plan`, then supply the complete current initial-body and per-file review with the same command without `--plan` and with `--review <review.json>`. Use `--scope project` for project availability. Plan standardization with `mise run standardize-target -- <source> --profile <profile>`, then apply its saved plan through `--apply --plan-file <plan.json> --review <review.json>`, preserving a valid scope. A legacy target also needs an explicit `--scope` after resolution. Import resolves scope before scaffolding its separate destination. Updates to instructions, scripts, references, assets, examples, or evals all count as changed skill output.

## Inspect legacy or accept output

`mise run validate-target -- <path> --inspect-legacy` inspects an untouched legacy skill. Missing scope remains missing. Invalid values, non-string types, malformed YAML, and duplicate keys still fail. Registry-wide read and inspection accept absent legacy scope and do not migrate any skill.

`mise run validate-target -- <path>` accepts changed output and requires a valid scope. Generated `mise run validate` uses the same strict acceptance flag, with its own copied checker. Standardization refreshes that checker and its task flag. Scaffolds retain their intentional unfinished-content gate. A scope pass alone never accepts unfinished behavior.

## Keep placement separate

An authoring destination stores a package. It does not determine scope. A metadata edit alone cannot install, relocate, duplicate, or change runtime permissions. For an operation that installs or places a skill in a host discovery directory, use the owning integration to verify the selected scope, target project, discovery roots, and name collisions first. Pass its current output with `--placement-receipt <file>` to new, standardize-target, or variant plan. Acceptance checks those roots again. Keep all client paths and resolution rules in the integration layer.

The repository's `mise run check-skill-destination` operation verifies the shared-directory integration. Other host conventions require their own verified integration receipt. If its rules or discovery roots cannot be retrieved, hold installation. Scope classification and authoring can still proceed where separately authorized. Do not claim universal host precedence from one adapter.

## Create a separate variant

A variant request creates a separate derived skill by default. Resolve the source package, actual source identity, target scope, unique variant name, destination, and target project when applicable. Read the whole relevant package: instructions, references, assets, scripts, configuration, tests, dependencies, license, attribution, and current eval evidence. Use `mise run plan-standardize` for the source inventory. Apply `mise run audit-source-corpus` only to a client-specific corpus import; it classifies client and package markers, not standalone portable skill packages. The source stays unchanged.

Run `mise run variant -- plan --source <source> --source-id <portable-identity> --scope <user-or-project> --name <variant-name> --dest <parent> --output <plan.json>`. A project target also requires `--project <project-root> --project-id <portable-project-identity>`. Save the JSON outside the source, candidate, destination, and target project. Use `--output` because Mise readiness output can share stdout; do not redirect mixed task output into a plan file. The plan reads complete owned file inventories and content digests, rejects symlinks, overlapping paths, a source-name collision, an occupied destination, and missing project context. Use an approved repository URL without credentials or query data, or an unambiguous portable identifier such as `repo:atlas` or `skill:file-inventory`.

A legacy source can be inspected without changing it. Resolve its intended scope first, then supply `--source-scope` when it has no designation. A valid source scope cannot be overridden by that flag. Every accepted variant must have exactly one valid scope.

Author the candidate in a separate directory whose name equals the variant name. Retain suitable content when it already works. Adapt only what the scope change requires; a renamed label is insufficient proof. Make every dependency available within the candidate or through explicit inputs, validated configuration, documented discovery, and stated compatibility limits. Review code before running its behavior drivers under the current user's authority.

For user to project, inspect the target project's authoritative instructions, structure, tools, commands, configuration, and constraints. Retrieve missing facts. Adapt applicability, inputs, instructions, references, examples, and validation to that project. Preserve the capability and every applicable requirement. Set `metadata.scope` to `project`; the accepted lineage records the portable target identity. Ask one concise question only when an unretrievable project fact changes the result.

For project to user, identify and preserve the transferable outcome. Replace project names, paths, identifiers, commands, configuration, and resources with explicit inputs, validated configuration, or discovery rules as needed. Remove credentials, private project data, and unnecessary source-specific material, including from metadata and public lineage text. Keep mandatory requirements enforceable and state compatibility limits. If a requirement cannot be generalized without changing purpose or weakening a mandatory constraint, resolve that limit before acceptance. Exercise at least two materially different project scenarios within those limits.

## Review and accept

The public factory `variant` and `validate-target` tasks depend on `check-runtime`, which depends on the existing locked `setup-runtime` task. An isolated factory prepares its own native checker dependencies before these consumers run. A missing or failed native checker remains a failure with its diagnostic; a prepared checkout is not a substitute for declaring this dependency.

Use the review shape in assets/variant-review.schema.json through `mise run variant`. First run `mise run variant -- review --plan <plan.json> --candidate <candidate> --output <review.json>`. It inventories the candidate and prepares an unaccepted draft with bound source and candidate digests. Fill every required field after review; empty draft fields fail acceptance. Cover every source file with a disposition and reason. Preserve other metadata and source-author attribution. If generalization requires replacing or removing private or project-bound metadata, document each necessary change in metadata_changes; acceptance rejects unexplained loss and includes those adaptations in lineage. Scope and the independently owned version are handled separately. For project scope, project_review also binds the project digest, covers its full relevant file inventory, and records authoritative instructions, structure, tools, commands, configuration, and constraints. Model review must substantiate those facts; the checker verifies coverage and binding. Record material adaptations, preserved requirements, compatibility, privacy and independence review, forbidden private markers, and behavior scenarios. The model must judge the meaning of these records; field presence is not semantic proof.

Each behavior scenario names a bundled Python driver, a project directory, the material difference it exercises, and exact expected stdout and exit status. The driver receives `--project <directory>` and may call the skill's declared tools. Use domain assertions, failure cases, and recovery tests. Run the candidate's own `mise run ci` before acceptance. For project scope, successful behavior must run against its declared project. For user scope, at least two successful cases need different project roots and material differences. Test in isolation from the source installation as well.

Run `mise run variant -- accept --plan <plan.json> --candidate <candidate> --review <review.json> --preview` first. Retain the complete returned `plan` object and exact output bytes outside every package and project input. Review every future file, including lineage, and every `retirements` entry against the complete current ledger, governing documents and candidate body. Each retirement contains the exact prior bytes and mode of an owned target path absent from the future package. The ledger review's `files` map covers the union of future and retired paths. Removed Python consumers precede their removed providers in the observed local import graph; this parser observation does not replace review of the actual ledger's full semantic removal relationships. Supply the existing initial-body review and every recorded file-review field in the same review shape used by new and standardize-target. Apply with `mise run variant -- accept --plan <plan.json> --candidate <candidate> --review <review.json> --plan-file <publication.json> --ledger-review <ledger-review.json>`. Keep the domain review separate from the per-file ledger review. Missing, incomplete, changed or stale inputs fail before staging. The preview executes source/domain review predicates but performs no publication writes or behavior execution.

Every staged file uses the shared source-aware writer with full before/after governing reads. Under the promotion lock, read the entire actual ledger and governing documents plus the actual old body separately for each retirement before publication. After publication, repeat those full reads with the current body for each retired path, verify final absence and compare its retained original bytes and mode before discarding the backup. Any failed check restores the prior package and preserves independent input edits. The returned `writes` history includes one `retire-file` record per actual removal, with the old identity and mode, absent new identity and mode, per-file review and pending execution acceptance. Save that history with the invocation evidence; it does not grant additional authority or prove semantic acceptance. Acceptance retains scope, identity, complete domain coverage, attribution, bounded private-data patterns, source independence, package contracts, eval schemas and actual behavior outputs. Recheck candidate, original source, project, destination, review and factory bytes and permissions before promotion and again under the shared package lock. Final verification uses the retained original backup for an explicit in-place change, compares the complete published files and directory modes, and excludes only the actual operation-owned stage, lock and backup paths from project context. Existing Git/runtime entries survive; failed final verification restores the prior package, and failed automatic restoration retains recovery directories. These checks execute reviewed code; they are not a sandbox, crash transaction or proof against deliberately concealed dependencies. Complete semantic source review and isolated behavior checks remain required.

The operation report identifies source and target, both scopes, material adaptations, whether source bytes were preserved, and each validation result. Package checks establish their stated structural contracts. Behavior outputs establish the exercised cases. Human or model review owns semantic adaptation, project fit, material scenario differences, and the completeness of privacy review. Do not call model judgment actual human testing.

## Lineage, reruns, and maintenance

The existing evals/source-lineage.json mechanism, read through `mise run lineage`, carries a `derivation` extension. It records actual source identity, version, full-package digest, both scopes, target project when applicable, material adaptations, requirements, compatibility limits, and source and target baselines. Source path keys are hashed in the derivation baseline so private source file names need not travel with a user variant. No source bytes or private filesystem paths are embedded. Keep required license and attribution files byte-exact.

Use a unique name so both source and variant can be available without unintended shadowing. An occupied destination fails. Repeating accept with the same scope plan and candidate after a successful creation is a no-op only while the previously published target content still matches and a fresh publication preview with a current ledger review binds the now-existing destination. A pre-publication review cannot be reused after the destination changes from absent to present. The no-op report names a reviewed rerun and retains `execution_acceptance: pending`; prior publication and current identity checks do not authenticate domain acceptance. A changed target fails safely. Never invent a suffix or create another variant automatically on retry.

Maintain source and variant independently. Updating either one never propagates to the other. A later variant records the package it actually derives from. Reversing scope does not promise restoration of original bytes or behavior.

For an explicitly requested source refresh, rerun plan with `--refresh`, the recorded source identity, and the existing variant destination. It compares current source files with the recorded source baseline and variant files with the recorded target baseline. A path changed on both sides is a conflict. This conservative file-level comparison also catches deletion conflicts. Preserve intentional variant customizations on paths without conflicts. Resolve every conflict in the review's `resolutions` map before acceptance. Combine compatible changes, retain an intentional customization, or ask for the one unresolved material choice. Update affected version and evidence after adaptation. Never overwrite customizations merely to make a refresh pass.

An explicit request to change the source in place uses plan with `--in-place`, the original name and destination, and the new scope. It requires all the same project, generalization, package, privacy, attribution, and behavior checks. The operation report states that the source change was explicit and does not claim preservation of its old bytes.

## Likely failure cases

Missing or conflicting scope holds the affected write. Malformed metadata fails even in legacy inspection. Missing project context holds project adaptation. Stale source or project digests require a fresh plan. Destination collisions and changed reruns preserve existing files. Lost attribution, private data, hidden source paths, unproved project fit, failed behavior, insufficient generalization scenarios, and unresolved refresh conflicts all block acceptance. Retrieve evidence or repair the lowest owner, then rerun only the invalidated checks.

Load examples/example-variant-project.md or examples/example-variant-user.md through `mise run variant` for the matching direction. Run `mise run test -- -k Variant` for the executable file-inventory cases and inspect their assertion results. These finite tests demonstrate the scope and adaptation contract for their stated inputs; they do not establish effectiveness for every future skill.
