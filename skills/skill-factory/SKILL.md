# Skill factory

## Outcome

Build portable skills that follow the [Agent Skills specification](https://agentskills.io/specification). Package their instructions and support files together, and state their tool and runtime needs. Update and maintain them. They must do their stated job in real use. This whole contract binds skill-factory. It also binds every skill the factory creates or updates. It binds skills the factory standardizes or imports. It binds skills the factory adapts or refreshes. It binds skills the factory invokes, checks or maintains. Cover all their files and outputs. Keep each skill's purpose. Keep accepted behavior and source bytes. Keep approved scope, independent variants and lineage. Leave unrelated work intact. Each required rule that applies must pass. A passed part cannot offset a missing required capability or proof. Nor can an average.

Read this whole body first. It owns the core rules, ledger method, file graph and first choices. On each load, capture all bytes of the current ledger and governing inputs. Review what each current rule and relationship means before use. Read each required initial resource before the work that needs it. Reuse a review only while its exact source, full scope and relevant context still match. Check changed or affected records, callers, dependencies and proof. A fresh builder must do any review it cannot safely reuse. Missing, stale, misrouted or ignored content or review blocks its consumer. A link, hash, receipt, acknowledgment or past load proves neither a meaning review nor current use. If work is delegated with permission, the invoking agent still owns integration and final proof.

Before affected writes, resolve scope and audience through `mise run resolve-scope`, `mise run use-case-policy` and the [scope contract](references/skill-scope-contract.md). `metadata.scope` must be one string: `user` for user-wide use or `project` for one project. The [use-case record][use-case] sets `audience.primary` to `human` or `agent`. This factory serves agents first and humans second. Use that record to label the early body and operation reports. Scope, executor, report recipient and location do not set audience. Keep valid choices unless an allowed change or a resolved purpose conflict requires a change. Reject bad values, types and duplicate keys. Untouched legacy inspection may allow a missing field; acceptance of a changed output may not. Resolve missing scope from clear intended use and authoritative context. Resolve primary audience from an explicit choice or authoritative purpose. If either remains unclear, ask one concise question before the affected write. Scope grants no right to install, move, copy or use a resource. Verify any allowed destination with the host integration owner. Record secondary and staged output audiences where they change requirements. Derive the role key below from the audience and ownership records. Use its meanings across the package and reports; do not copy the full key into each file.

- **Duties.** Before each operation, name who reads, writes, acts, judges, verifies and validates. For a read, name the actor, resource, load trigger and freshness. For a write, name the author, allowed tool, where it may save, and what it may change. For an action, name who runs it, its callable interface, inputs, effects and next owner. Give meaning and context judgments to a capable model or human. State their criteria and proof. Use capable checks to verify the actual rules. Validate the combined result for its audience and context. Final acceptance has its own authorized owner.
- **Human or agent consumer.** For humans, judge whether the result meets the real need. Name any required human choice or observation. For agents, check the interface, meaning, failure handling and real downstream use. Keep duties to affected people. Judge what the consumer must do next. The report recipient, executor and folder do not set the primary audience. If the audience changes, adapt the inputs, instructions, interfaces, presentation, evals and human role.
- **Model.** Judge what the work means and what matters. Weigh proof and cause and effect. Research, use perception and create only when allowed. Code cannot force these judgments to repeat the same result. Name the real model used for each review. State its input and output types, proof, criteria and limits. Model review is never human evidence.
- **Human.** Name the real people and their roles. Include those who request, design, maintain, run or receive the work. Include people it affects, domain experts and participants. Include reviewers, approvers and owners of resources or permissions. One person may hold several roles. Obtain each assigned real decision, preference, review, observation and proof of task performance. Name its kind, role, context and artifact. Permission, preference and task performance are distinct. Personas and model judgment cannot replace people.
- **Program and host.** Find the actual [Mise][mise], [Mastra][mastra], scripts, [Usage][usage], [hk][hk], [Packslip][packslip], [Pitchfork][pitchfork] and [fnox][fnox] participants. Include language and package tools. Include domain tools and services. Include the systems that run work, keep state and store data. Each must run its stated repeatable operation through its supported interface. For mechanical proof, name the deterministic rule, captured inputs, result and coverage. It cannot prove an untested subjective response. Startup, generated commands and exit status do not prove the intended effect. Finding a tool grants no right to activate or use it. Check the host's real identity and permissions. Check its input and output types and how it can communicate. Task data grants no right to run code or use the file system.
- **Acceptance owner.** Name the real software, model and human evaluators. Name the source and release authorities. Verify the stated properties. Then validate the combined result in its real context. Bind each claim to its inputs, outputs, versions and proof. Delivery, consumption and acceptance are distinct. Required gates limit actions and claims. Declared creative choices stay open. Missing required proof blocks the action or claim that needs it. Optional feedback, hypotheses and pending work cannot earn a pass.

## Motivation

Turn intent into skills that can be used. Make its reasons, actions and proof open to review. For each rule that matters, state the outcome it protects and the failure it prevents. Keep valid alternatives. Keep uncertainty, intelligence, creativity, craft and taste. A part can be sound in a technical sense and still fail its task.

Simple means clear and complete under the contract. Keep one owner for each meaning, one stable term and one default route per real choice. Set context budgets from the domain work, its risk and required proof. Reuse each canonical owner. Keep required full reads, domain judgment and context. Reuse existing code, native tools and accepted structures before adding dependencies. Remove content only when its consumers and ledger relationships prove it serves neither the outcome nor the skill's integrity. Fewer files, lines, connectors, tokens or seconds cannot justify lost rules. They cannot cut domain complexity, safety, privacy, accessibility, authority or proof. Choose algorithms, data structures and formats from measured needs. Check access, writes, queries, order, interoperability and lifetime. Use those same needs to choose batching and concurrency. Reuse native streaming, indexes and atomic replacement only within their real guarantees. Keep valid unexpected reasoning and solutions. If this cannot be done, use the verified complete authorized baseline or block the affected consumer. Never weaken acceptance. The graph tracks specifications and helps organize successful use. Judge the architecture by complete factory and output-skill outcomes. Counts only support that judgment.

Prevent WorkSlop: output that fails its task or leaves the recipient to finish its reasoning, checks or repair. Find the real need. Finish the producer's work, verify its claims and make the result usable. Through `mise run domain-research-policy`, consult relevant original [research](https://www.betterup.com/workslop), [preprint](https://doi.org/10.31234/osf.io/5f78h_v1) and [survey](https://zapier.com/blog/ai-workslop/). Keep their methods, populations, context and uncertainty. Consider real working conditions, culture, agency and meaningful purpose. Adoption and attractive presentation do not prove useful or causal improvement. Neither do subjective satisfaction or commercial associations. Review [Case for Conditions](https://www.betterup.com/the-case-for-conditions) and [workplace-culture findings](https://www.betterup.com/blog/ai-watermarking-workslop-culture) for relevant purpose, workload, trust and agency. Keep self-reports, associations, preprints, commercial advice and causation distinct. Do not combine separate samples or call estimated costs measured losses. Seek contrary proof and newer findings. Reward useful outcomes and honest correction. Make flawed inputs and uncertainty easy to report. Keep meaningful human control.

Reconcile equivalent rules at their existing owner. State defaults and exceptions. Use `mise run ledger` with `check-capture` to check recorded bytes and locators. ## Mise task graph

[Mise][mise] owns public commands, pinned environments and outer prerequisites. [Mastra][mastra] owns substantive domain control, state and recovery. Existing tested scripts perform repeatable leaves; caller-controlled models and actual humans perform their assigned judgment. Keep one owner for scheduling, retries, caching, state, effects and cleanup, with explicit handoffs. Isolate actually repeated workflows in their existing public [Mise][mise] task or appropriate [Mastra][mastra] workflow; route all callers through that owner and propagate this rule to every output. Never add competing recursive [Mise][mise] graphs or replace required [Mastra][mastra] domain work with bookkeeping.

| Command | Route and result |
| --- | --- |
| `help` | Show this grammar and one-line results; `mise run validate` owns the [help example](examples/example-help.md). |
| `new <prompt>` | Resolve name, description, scope, audience and destination. Use `mise run new -- --name <name> --description "<description>" --scope <user-or-project> --dest <destination> --plan`; review exact bytes and repeat with `--review <review.json>` instead of `--plan`. A scaffold remains unaccepted. |
| `update <path> <prompt>`; `standardize <path>` | Freeze the baseline with `mise run plan-standardize -- <path>`, then use the supported reviewed operation and validate the complete target. |
| `standardization-usage`; `standardize-target <path> <profile>` | `mise run --output interleave standardization-usage` exports the native [Python][python] argument definition through pinned [Usage][usage]. `mise run --output interleave standardize-target -- <path> --profile <profile>` plans the actual domain workflow. Load the [standardization procedure](examples/example-standardization.md) for scope, reviewed apply, persistent state, rejection, replay refusal, recovery and proof limits. |
| `import <source> <destination>` | Run `mise run audit-source-corpus -- <source>` and `mise run plan-standardize -- <source>`; preserve/classify the whole source before the supported separate-destination conversion. Grammar does not invent a missing interface. |
| `variant <source> <user-or-project>` | Use `mise run variant` and the [variant contract][variants] for scope planning, adaptation, domain review, publication preview, per-file/retirement review and guarded acceptance. |
| `validate <path>`; `eval <path>` | Run `mise run validate-target -- <path>` and `mise run eval-target -- <path>`, then the actual declared evaluation runner. `--inspect-legacy` cannot accept a changed output with missing fields. |
| `refresh-registry-lineage <skill...>` | `mise run refresh-registry-lineage -- <skill...> --plan` exposes changes; its `--review <request.json>` applies only the next dependency-ordered file. Replan until empty, then validate the whole result using [file review][file-review]. |
| `doctor` | `mise run doctor` reports actual supported readiness and the precise missing prerequisite. |

## Steps

Start with the matching public command in the Mise task graph. Use the seven stages below for creation and maintenance. Each stage needs real Mise tasks, Mastra step IDs, declared inputs and outputs, direct dependencies and current proof. Mise prepares runtimes and prerequisites. Mastra owns domain state, waits and recovery. It never calls nested Mise or its entry task. Check prior proof without repeating completed effects. Missing owners or failed guards block the steps that need them; written instructions alone are not working code.

1. **RECONCILED.** Model: read this whole body and the required initial inputs using the load and review rules above. Bind the command, outcome, audience, scope, accepted behavior, fixed rules, methods and proof. Host: verify identity and rights. Model and [Mise][mise]: inspect the source, package, environment, interfaces, callers and graph. Run doctor and the policy routes that apply. Keep exact versions, modes, source bytes and the skill baseline. Missing sources or changed identities block affected work; never rewrite a source to hide drift. Use the scope and use-case owners to map load routes, work owners and acceptance paths. Through the ledger workflow, check all source coverage, file roles, links and body duties. Add missing records and keep their parents. Finish the required whole-body foundation and fresh candidate review before later file work. Use an approved prerequisite exception only with its actual authority and named pending checks. Human clarity and same-meaning proof still need final acceptance. Record current input identities, valid meaning reviews, graph/ledger fit and open duties. Explore open questions within the fixed effect and acceptance gates. Answer help or doctor requests with their declared results; otherwise keep the chosen operation. Ask only for a material fact that cannot be found or for required authority. Factory work uses this process; each output runs its own domain workflow and reusable checks.
2. **SELECTED.** Model: choose a named open source duty and show the gap in its code or instructions. Start at SKILL.md, then files one connector away, then two, and so on by shortest valid path. Follow real prerequisites and approved exceptions. Resume eligible unfinished work before other preparation. Use the existing adaptation policy to break ties. A missing path is a defect, not a reason to invent a layer.
3. **READY.** Model and [Mise][mise]: fix the ordered plan before acting. Name its inputs, owners, resources, effects, readbacks, tests, recovery and needed changes in other files. Use `plan-standardize`, keep `baseline_digest`, and use `task-graph-policy`. Imports also need a source-corpus audit. Follow the exact reviewed branch for standardization and variants. Check collisions, ownership, layers and real prerequisites. Bind each file's identity and lineage to its current and planned typed path to SKILL.md, distance, body rule, need, intended effect and deciding check. Check rights, required reads and allowed changes before each effect. Once ready, make the change before optional preparation.
4. **IMPLEMENTED.** [Mastra][mastra] executes the domain plan with real scripts, allowed runners and assigned model or human judgments. Use the per-file reads, graph review and change history above. For new skills, build tasks and CI/graph contract tests first. Observe a failing behavior test, write the smallest sound change, then update docs and evals. Use focused RED, GREEN, REFACTOR and affected regression checks. Reject placeholders, generic profiles, unsupported interfaces, lost behavior and source changes without authority. Keep exact before/after bytes, modes, diffs and observed effects. Keep each failed attempt. If an effect is unclear, inspect it before retrying. A receipt or run ID does not prove that an effect happened just once.
5. **VALIDATED.** Model: run the assigned checks and obtain required real human or recipient proof. Run `mise run decision-policy`, the target's full `mise run ci`, `validate-target`, `eval-target` and the actual case runner. Inspect exact artifacts in their real media. Check source support, domain effects, required non-effects and safe recovery in independent outputs. A factory pass cannot hide an output failure. Fix the lowest failed owner and mark affected dependent proof stale. Bind proof to exact resulting inputs; keep them unchanged while checks run. Complete the post-read, body integration, file-path and preservation checks. Reject stale, unrelated or unsupported proof. Approved prerequisite work leaves missing integrated or human proof pending.
6. **FINALIZED.** Model: review each changed file as a whole. Check its source duties, known callers, downstream needs, Markdown clarity, physical size/depth limits and graph/ledger fit. Keep enough content to meet those needs. Reject needless layers, duplicate owners, cosmetic churn and speculative additions. Hardening proves the current contract, not that a file will never need repair. Pending proof is still not acceptance.
7. **ADVANCE.** Model: record each public task's real run or source-backed domain non-use with `mise run invocation-policy -- <receipt>`. Use the controlled-improvement and prior-adoption checkpoint in Evals. A trial needs a real need, authority, accepted required work, full proof and a safe restore budget. After outcome and acceptance work, run `mise run mise-primitives-update` last through its reviewed catalog/lineage branch. Its predependency updates [Mise][mise] without plugins. Its body refreshes the exact-release schema catalog. Its postdependency requires domain review and lineage refresh. Run full CI again with that binary. Check exact local, installed and authoritative remote contents, discovery, invocation, independent outputs and CI for that revision. Honor release rights. For a PR merge, first pass all non-merge proof, then obtain actual merge approval, then verify main and final delivery. Keep every other acceptance duty. Record the source duty, file/lineage, turn, purpose, diff, intended and observed effect, validation, acceptance owner, remaining gap and next action in the existing ledger/changelog. Keep implementation, validation and acceptance distinct. Only necessary changes with fresh effect proof earn progress; graphs, bookkeeping and unchanged reruns do not. Compare correctness first; compare speed only with matched whole-workload proof. Keep the baseline and change history for the next eligible loop. Stop only when the full result is accepted, never just because one loop ended.

An attributable regression requires restoring the complete pre-trial owned change set, modes and supported creations/retirements through the reviewed writer/promotion owner. Compare baseline, candidate and current state; preserve independent edits/variants and resolve overlap. Revalidate restored consumers and stale proof. Unknown safety/correctness blocks reliance; missing safe restoration blocks adoption. Retain no-op, pending, keep, discard, crash and restoration evidence. Improve this process through independent held-out end-to-end comparisons.
- Every action must advance a required skill-file change, validation or delivery. Close the smallest ready functional path through required gates, proof and authorized delivery. Tie reads, research, infrastructure, graph/ledger work and packaging to the specific change or outstanding proof they enable; complete the prerequisite, then perform the eligible change. Private drafts, plans, reports, queued jobs, cosmetic churn and repeated unchanged checks alone are not implementation progress. Real implementation progress requires a necessary skill-file change tied to a named obligation, followed by evidence of its intended effect and required validation. An applied but unvalidated change remains implemented with validation pending. Use the existing changelog and ledger to bind file, source requirement, purpose, actual effect, validation result, remaining gap and next dependent action. Keep proposed, implemented, validated and accepted states distinct. Preserve every gate; resolve verified blockers or advance another eligible change. Never manufacture edits after implementation. Reuse valid unchanged evidence with current bindings unless repetition is required; retain every mandated full read and integrated check. Change ineffective approaches using observed failures/timing. Propagate this policy into actual output bodies. Standardization reads the current canonical efficiency paragraph from the template; differing existing text requires an explicit reviewed migration, never silent replacement.
- Use [outcome and resource measurement](references/eval-authoring.md#outcome-and-resource-measurement) to compare accepted factory invocation, skill creation/update, output invocation and maintenance. Measure matched cold/warm complete paths, including reading, failures, recovery, verification, actual tokens and recipient effort. Separate external waits, uncertainty, estimates and missing counters. Avoid double-counting concurrent work or calling required review waste. Optimize measured bottlenecks without protected regression; microbenchmarks do not prove whole-result savings.
- Accept only fresh sufficient evidence for every applicable requirement across the factory, required outputs, operations and integrated use. Bind exact subjects/revisions/bytes, source, actual inputs/resources/selections, dependencies/environment/engine/schema/evaluator, authority, protocol, domain effects, artifact provenance and responsible judgment. Missing, failed, stale, blocked, indeterminate or unapproved mandatory work cannot be averaged away. Human/physical evidence remains pending when unavailable. Preserve license, attribution, versions, installation/publication authority and read-only path-confined repository MCP limits; add no unrequested telemetry, credentials or integrations.
- Return the required decision trail for purpose/audience, issues/owners/changes/proof, body/load guide, all requirements/operations/outputs, dependency discovery/order/readiness/invalidation, enforcement perimeter/rejection/recovery, meaning/variation, tools/resources/versions, [Mastra][mastra]/human/A/B/C, language/Ponytail, matrix coverage/participants/transfer limits, anti-patterns, measured resources/scalability, variants/lineage and local/remote delivery. Distinguish implementation, validation and accepted obligations; state percentage denominators/weights and uncertainty.
