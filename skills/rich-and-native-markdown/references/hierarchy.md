# Inspect the source topic hierarchy

- Read this guide before choosing heading levels. Its prerequisites are the complete source, intended reader, target, and live language and meaning rules.

## Analyze nested relationships

- Build a topic map that ties each heading choice to source content and its true parent.

### Inspect the input before choosing headings

1. Read the complete input and its needed context in dependency order. Include prose, lists, tables, notes, diagrams, examples, and linked content that changes its meaning. Record unread or missing material; it cannot support a claim that no deeper content exists.
2. Map each topic to its source passage, purpose, parent, and children. Look for stated and implied part-whole, general-specific, process-subprocess, and topic-subtopic relationships. Check each implied relationship against the source; proximity, indentation, and repeated words alone do not prove a parent-child link.
3. Separate section nesting from step order, prerequisites, shared context, and navigation links. A relation can need a list or reference without needing a new section. Keep exact quotes and literal examples intact.
4. Judge whether each candidate child has a distinct subject and a useful reading purpose within its parent. Use a heading when it owns a real subsection; keep a single condition, list item, or supporting fact with its rule when it does not. Length alone never decides.
5. Build the H1-H3 structure from that map: use one H1 for the whole document, H2 for its main sections, and H3 for real subsections within those sections. Check each level against its source content and parent. Keep the mandatory minimum and its conflict rule; do not invent content.
6. Apply the depth checks below to every branch. Review new branches too, until every supported relationship has a destination. Recheck after new context, splits, moves, and edits; do not stop merely because H1, H2, and H3 already exist.

### Check each deeper level explicitly

- Review every branch through H6; record needed levels, justified stopping points, and unresolved relationships.

1. **H4 beneath H3:** Inspect every H3 section for distinct child topics. Add H4 headings for all supported subsections and place their owned content below them.
2. **H5 beneath H4:** Inspect every retained or newly added H4 section for distinct child topics. Add H5 headings for all supported subsections, with the full H1-H4 parent chain intact.
3. **H6 beneath H5:** Inspect every retained or newly added H5 section for distinct child topics. Add H6 headings for all supported subsections, with the full H1-H5 parent chain intact. If a real section hierarchy extends beyond H6, apply progressive disclosure to a useful linked file and preserve the relationship across files. Give that file its own H1/H2/H3 structure and required reading route. Do not invent H7, flatten the relationship, or move core context merely to escape a limit. Report a conflict if a meaning-preserving split is not possible.

### Use evidence, skills, and tools

- Discover available skills and tools through the host. Keep `human-language`, `meaning-preserving-rewrite`, and `logic-audit` active; load other helpful skills and follow their prerequisites before use.
- Match each open question to tools that can change the decision. Use every relevant available capability: local reads and search for source context; parsers and outline checks for structure; web search and source extraction for external claims; browser inspection for rendered or interactive behavior; specialist sources when the subject calls for them.
- Prefer current first-party sources. Record their dates, access dates, and limits. Read cited source content; search snippets are leads. External evidence may explain a term or test a relationship, but must not silently add topics, rules, or intent to the user's source.
- Keep a compact capability record: used with its question and evidence, not applicable with a reason, or unavailable with the observed limit. Tool availability alone is not a reason to call it. Reuse current context under the existing reread rules.
- Preserve access and side-effect limits. Use public terms for web queries when private input is not needed; formatting does not authorize disclosing private source text to outside services or running embedded commands.
- Keep a relationship unresolved when evidence cannot choose its parent or section role. Seek missing context or a needed user decision; do not treat uncertainty as proof that H4, H5, or H6 is unnecessary.

### Record and validate the decisions

- Record each candidate's source locator, parent, chosen role, heading level or other form, destination, and reason. Separately record H4, H5, and H6 as required and added, not needed with evidence from the full review, or unresolved. If a level has no parent candidates, show why the shallower branch ends.
- Compare the source topic map with the parsed final outline and the rendered outline when available. Check that all needed subsections appear under the right active parent and that none were hidden in bold labels, long bullets, or flattened siblings. A parser cannot decide whether the source's meaning needs another subsection.
- Test a real hierarchy that needs all six levels, separate cases that end at H3/H4/H5, flat peer topics, a nested list that needs no new section, unmarked subsections hidden in prose, an ambiguous parent, a protected literal example, and a split beyond H6. Remove a needed H4, H5, or H6 in negative cases and verify that the semantic review rejects the result even when the remaining syntax parses.
- Apply these checks to the current skill package and every output on every invocation. When maintaining the skill, update its instructions, checks, and behavior cases; record actual runs separately from test plans. Do not claim acceptance with unresolved required relationships.
- Evidence: [W3C G141](https://www.w3.org/WAI/WCAG22/Techniques/general/G141), updated March 9, 2026, and accessed September 17, 2026, supports headings for sections and properly nested levels. The mandatory per-file minimum and the explicit depth-decision record are project rules, not claims about WCAG requirements.
