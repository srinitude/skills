# Skill factory

- **Start here.** On every load, read this whole SKILL.md body first. Run `rule:read`, owned by [load tasks](tasks/context.toml). If its tool is not connected, use `mise run rule:read`. Bind exactly one `body` input: this skill’s real SKILL.md path, current hash and full text. Reject other paths, byte-only input and duplicate body roles before model work. Read the full `task-tools` body through its tool's inspect action; if tools are not connected, use `mise tasks info task-tools --json`. Follow its connection, task-call and model-handoff rules. Use the [Mise task graph](#mise-task-graph) and [Steps](#steps) to select work.
- **Read and retain context.** Run `mise run rule:context`, owned by [load tasks](tasks/context.toml), after the whole-body read. It owns source capture, meaning review, valid review reuse, missing-input recovery and integration duties. Read its full rules before work uses that context.

## Mise task graph

- **Work owners.** [Mise][mise] owns public commands, pinned environments and outer prerequisites. Always start or resume [Mastra][mastra] workflows through their declared [Mise][mise] tasks. Do not call workflow launchers directly. [Mastra][mastra] owns substantive domain control, state and recovery. Existing tested scripts perform repeatable leaves. Run every script, including files in the scripts directory, through its declared task (`mise run <task>`) with its real prerequisites. Pass every skill file, including evals, examples and references, as input to a named task for its required use or checks. Do not turn model-owned work into pretend code checks. The model owns all work it does best, including creative choices, meaning and direct perception with its available tools. Required human judgment stays with its human owner.
- **Rule coverage.** Each task body has five parts: Why this runs, When to run, Inputs, Work, and Proof. Pass its full native Mise text and required resources to its own Mastra workflow. Map every rule to a named Mise task, its individual agent tool and its own Mastra workflow. Keep each required model or human review. Apply this to task and workflow creation and every generated or updated skill. Keep one owner for scheduling, retries, caching, state, effects and cleanup, with explicit handoffs. Isolate actually repeated workflows in their existing public [Mise][mise] task or appropriate [Mastra][mastra] workflow; route all callers through that owner and propagate this rule to every output. Never add competing recursive [Mise][mise] graphs or replace required [Mastra][mastra] domain work with bookkeeping.

Request data cannot change that mode. Validate exact bytes, nonempty UTF-8 content and dependency order; require one governing ledger and the relevant matrix/resources. Define required status, meanings, path resolution and validation; use files or stdin for long content. Account for every published task, running required tasks and recording source-supported inapplicability. Every task reaches CI or a public operation. Inspect all effective inherited/template sources, aliases, patterns, native arguments, `run`/`run_windows` references and environment. Sibling list order is not sequencing; parallel groups differ from sequential run entries.

They provide neither permission nor accepted parent output, rollback or crash recovery. Preserve task-environment non-inheritance and selected-version template behavior, including empty child `depends` not necessarily clearing inherited prerequisites. Verify native behavior. Task includes do not deliver model context; [Usage][usage] declarations do not prove forwarding.

Preserve existing languages, caller-controlled runners and faithful modalities. A one-node proxy cannot satisfy this requirement. Enforce required predicates before effects, suspend before protected work, validate schemas and current identities, bound retries/concurrency and preserve authentic approval. Keep engine-specific states, storage/replay, dynamic definitions, scheduling and privacy limits explicit. Stored state, successful transport and completed streams do not prove domain success, durability, crash safety or exactly-once effects.
- Bring a human in when required, or when a targeted interaction is the best authorized way to resolve material uncertainty or improve the outcome. Choose the method from the question and required evidence; do not wait for exhaustive research or ask people to repeat available mechanical work. For that interaction, the model prepares the concrete artifact, permitted checks, material question and assigned role. The human supplies actual input or remains pending. Scripts validate identity and unchanged bindings; the model judges meaning before supported resume. Silence, timeouts, defaults, personas, duplicates, stale replies and labels are not approval. Revisions stale affected approval/evidence. Reuse valid input, respect rejection and continue eligible independent work.

Keep the first protected effect behind the gate. Optional unavailable studies support only narrower claims; required human proof remains pending. Feedback grants no silent change to installed skills, source, variants, preferences or memory.

A cannot replace mandatory [Mastra][mastra]. Repeat small, typical and larger workloads across success/failure, fresh/reused starts, interruption and recovery. Measure setup, dependencies, build/import/startup, processes, serialization, snapshots/writes, traces, CPU, memory, network, model work, waits, retries, cleanup and recipient effort. Separate engine overhead using actual counters. Choose the simplest fully compliant demonstrated tradeoff; reject blanket wrapping that adds cost or weakens control/recovery. Report the exact conflict if none qualifies. Inspection and upstream benchmarks do not prove these results.

## Steps

Start with the matching public command in the Mise task graph. Use the seven stages below for creation and maintenance. Each stage needs real Mise tasks, Mastra step IDs, declared inputs and outputs, direct dependencies and current proof. Mise prepares runtimes and prerequisites. Mastra owns domain state, waits and recovery. It never calls nested Mise or its entry task. Check prior proof without repeating completed effects. Missing owners or failed guards block the steps that need them; written instructions alone are not working code.

1. **RECONCILED.** Model: follow the full load and review rules. Bind the command, outcome, audience and scope. Bind accepted behavior, fixed rules, methods and proof. Host: check identity and rights. Model and [Mise][mise]: inspect the sources and package. Check the environment, interfaces, callers and graph. Run doctor and each policy task that applies. Keep exact versions, modes, source bytes and baseline. Missing or changed sources block work that needs them. Never rewrite sources to hide drift. Use scope/use-case owners to map load, work and acceptance routes. Check source coverage, file roles, links and body duties through the ledger. Keep parent records. Complete the whole-body foundation and fresh candidate review. Exceptions need approval and named pending checks. Human clarity and same-meaning proof stay required. Explore within fixed gates. Ask only for material facts that cannot be found, or required rights. Return help/doctor results; otherwise keep the chosen operation.
2. **SELECTED.** Model: choose a named open source duty and show the gap in its code or instructions. Start at SKILL.md, then files one connector away, then two, and so on by shortest valid path. Follow real prerequisites and approved exceptions. Resume eligible unfinished work before other preparation. Use the existing adaptation policy to break ties. A missing path is a defect, not a reason to invent a layer.
3. **READY.** Model and [Mise][mise]: fix the ordered plan before acting. Name its inputs, owners, resources, effects, readbacks, tests, recovery and needed changes in other files. Use `plan-standardize`, keep `baseline_digest`, and use `task-graph-policy`. Imports also need a source-corpus audit. Follow the exact reviewed branch for standardization and variants. Check collisions, ownership, layers and real prerequisites. Bind each file's identity and lineage to its current and planned typed path to SKILL.md, distance, body rule, need, intended effect and deciding check. Check rights, required reads and allowed changes before each effect. Once ready, make the change before optional preparation.
4. **IMPLEMENTED.** [Mastra][mastra] executes the domain plan with real scripts, allowed runners and assigned model or human judgments. Use the per-file reads, graph review and change history above. For new skills, build tasks and CI/graph contract tests first. Observe a failing behavior test, write the smallest sound change, then update docs and evals. Use focused RED, GREEN, REFACTOR and affected regression checks. Reject placeholders, generic profiles, unsupported interfaces, lost behavior and source changes without authority. Keep exact before/after bytes, modes, diffs and observed effects. Keep each failed attempt. If an effect is unclear, inspect it before retrying. A receipt or run ID does not prove that an effect happened just once.
5. **VALIDATED.** Model: run the assigned checks and obtain required real human or recipient proof. Run `mise run decision-policy`, the target's full `mise run ci`, `validate-target`, `eval-target` and the actual case runner. Inspect exact artifacts in their real media. Check source support, domain effects, required non-effects and safe recovery in independent outputs. A factory pass cannot hide an output failure. Fix the lowest failed owner and mark affected dependent proof stale. Bind proof to exact resulting inputs; keep them unchanged while checks run. Complete the post-read, body integration, file-path and preservation checks. Reject stale, unrelated or unsupported proof. Approved prerequisite work leaves missing integrated or human proof pending.
6. **FINALIZED.** Model: review each changed file as a whole. Check its source duties, known callers, downstream needs, Markdown clarity, physical size/depth limits and graph/ledger fit. Keep enough content to meet those needs. Reject needless layers, duplicate owners, cosmetic churn and speculative additions. Hardening proves the current contract, not that a file will never need repair. Pending proof is still not acceptance.
7. **ADVANCE.** Model: record each public task's real run with `mise run invocation-policy -- <receipt>`. Any domain non-use needs source support. Apply Evals' improvement and prior-adoption checks. Trials need a real need, rights, accepted required work, full proof and a safe restore budget. After outcome and acceptance work, run `mise run mise-primitives-update` last through its reviewed catalog/lineage branch. First its prior task updates [Mise][mise], with no plugins. Next it refreshes the schema catalog for that exact release. Its post-task requires domain review and lineage refresh. Rerun full CI with that binary. Check exact local, installed and authoritative remote contents. Check discovery, invocation, independent outputs and CI for that revision. Honor release rights. Before a PR merge, pass all non-merge proof and obtain actual merge approval. Then verify main and final delivery. Keep all other acceptance duties. Use the ledger and Evals' progress rules to record effects and remaining work.

- Review the whole file first: its purpose, reader, required rules, structure, order and fit with the skill. Next review its sections and blocks. Polish lines last. Judge Markdown forms, spacing and plain language together. Then read the full result again. Use `mise run markdown:inventory`, `markdown:mechanical`, `markdown:review-request`, `markdown:macro-review`, `markdown:micro-review`, `markdown:line-review`, `markdown:review-check`, then `markdown:accept`. Run each through `mise run`; each task names its real prerequisite. Load the [writing rules](references/writing-rules.md) for this review. Within this skill, check each sentence, rule, section, file and cross-file relationship for kept meaning and alternate readings. The [rewrite method](https://github.com/srinitude/skills/blob/main/skills/meaning-preserving-rewrite/SKILL.md) and [ambiguity method](https://github.com/srinitude/skills/blob/main/skills/only-one-interpretation/SKILL.md) are sources, not required installed skills. Map source clauses to replacements and back. Test alternate readings, conflicts and exceptions. Human same-meaning review checks clarity and completeness. Lexical lint cannot replace it.
- The current model runs the tasks and reads their full results and errors. Each task returns one full bound review payload. Omit only exact duplicate payloads from printed step traces; keep all unique diagnostics and the saved execution record. Give it the exact text, source rules, affected links, prose findings and readable renders. It must judge the assigned question, then send its reply to the same pending run.
- Each reply needs reasons and cited proof. For every Markdown feature, explain what it is, which form fits, when and how to use it, why it helps, and who writes, checks and approves it. Cover the full named standards and target extensions; choose only forms the content needs. Check meaning, clear actions, terms, structure, first-load rules, file graph fit and honest score exclusions. Bind the full feature map and reply to the same turn, baseline, run, step, file bytes and policy versions.
- Check each reply against its schema, exact inputs and passed prior stage. Keep required reads, safety and integrity checks before each change. Early quality findings must reach the model for whole-file review; they still block final acceptance until fixed. A line check cannot replace whole-file or section review. Changes stale affected proof. Resume at the earliest affected stage and keep missing model, human or integration proof pending.
- Test failure and recovery through the real tasks. Include stale replies, skipped gates and repeat resume. Check saved-state recovery and protection from concurrent writes on the actual runner. A passed task alone cannot prove these properties.
- Mastra calls the shared owners directly. It must never call nested Mise. Keep the model's judgment distinct from human authority. A local checker that the agent can edit provides cooperative checks, not independent enforcement.

## Assets

- Each accepted skill owns one matching directory, [SKILL.md][body], necessary support, `mise.toml`, CI, complete examples and evals. YAML starts at byte zero with supported fields only: name, description, license, compatibility, metadata and allowed-tools. Reject duplicate keys and invalid types.
