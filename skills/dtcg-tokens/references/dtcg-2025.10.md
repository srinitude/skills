# DTCG 2025.10 authoring rules

Target the stable Design Tokens Format Module 2025.10 and set root `$schema` to `https://www.designtokens.org/schemas/2025.10/format.json`. The pinned copy in assets/dtcg-format-2025.10.schema.json is the validation baseline.

## Core shape

A token is an object with `$value` or a JSON Pointer `$ref`, plus a resolvable `$type`. Groups may inherit `$type` and may contain `$description`, `$extensions`, `$deprecated`, `$extends`, and `$root`. Use `$description` for intent that a token name cannot carry.

Token and group names must not start with `$` or contain `.`, `{`, or `}`. Keep names stable, semantic, and lower kebab case where compatibility permits. Avoid embedding platform units or implementation names in semantic paths.

## Standard types

The standard types are `color`, `dimension`, `fontFamily`, `fontWeight`, `duration`, `cubicBezier`, `number`, `strokeStyle`, `border`, `transition`, `shadow`, `gradient`, and `typography`.

Color values use `colorSpace`, three typed `components`, optional `alpha`, and optional six-digit `hex`. Dimensions use numeric `value` with `px` or `rem`. Durations use nonnegative numeric `value` with `ms` or `s`. Cubic Bezier values hold four numbers and constrain the two x coordinates to 0 through 1.

Composite values use the exact member types defined by the format. A border contains color, width, and style. A transition contains duration, delay, and timingFunction. A shadow contains color, offsetX, offsetY, blur, spread, and optional inset. A gradient contains at least two color and position stops. Typography contains fontFamily, fontSize, fontWeight, letterSpacing, and lineHeight.

## References

Use curly-brace aliases such as `{primitive.color.ink}` for whole-token references. Use JSON Pointer reference objects such as `{"$ref":"#/primitive/color/ink/$value"}` where the format permits a subvalue reference. Every target must exist, type compatibility must hold, and the graph must be acyclic.

## Architecture

Use primitives for observed raw values, semantic tokens for meaning, and component or pattern tokens only where the input supports a reusable consumer. Prefer aliases over repeated literals. Avoid aliases between incompatible types and avoid deep chains without a semantic reason.

## Extensions

Use namespaced `$extensions` for concepts without a standard DTCG type, such as asset references, layout grids, breakpoints, variable-font axes, light direction, texture recipes, or platform transforms. Do not invent a `$type` for them. Document the namespace owner and value schema in the output.

Every generated set also contains a top-level `experimental` group with at least two tokens from two distinct enumerated exploration strategies. The group uses `$extensions.org.dtcg-tokens.experimental` with `required: true` and `policy_version: 1.0`. Every token beneath it remains a valid standard DTCG token or a documented extension value and carries the same namespace with `experiment_id`, `exploration_strategy`, `hypothesis`, `intended_context`, `status`, and `invariant_disposition`. Experimental tokens are real output tokens, not comments or sidecar suggestions.

## Validation meaning

The bundled validator checks names, supported properties, standard types, value shapes, references, type agreement, and cycles, and reports the pinned schema hash. It does not prove downstream tool support or visual quality. Keep those claims separate.
